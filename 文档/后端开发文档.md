# Back-end development guide: memory, agents, plaza, evolution, knowledge

English | [中文](后端开发文档.zh.md)

## Scope

This guide turns [the product design](2026-11-18-consumer-memory-agent-product-design.md) into buildable Host work on the real `dsh` architecture. It states which packages own which behavior, which Remote namespaces the Client calls, which durable facts are recorded, and which guards a production deployment needs.

The Host is a Cordis plugin tree too. A new capability is a package that contributes a service, events, and registration effects; the Client reaches it through a Remote namespace generated from `@Remote` descriptors by `@deepseek-ai/dsh-api-gateway`. Nothing here adds a second composition model.

## Architecture placement

| Layer | Package | Role |
|---|---|---|
| Capability seam | `packages/memory/memory` (existing) | Service Definition for long-term memory |
| Knowledge seam | `packages/knowledge/knowledge` (new) | Service Definition for citable knowledge, beside memory, not inside it |
| Providers | `memory/memory-bear` (existing), `knowledge/knowledge-<vendor>` (new) | Vendor storage and retrieval |
| Consumers | `memory/memory-autosave`, `memory/tool-memory`, `memory/memory-agent` | Turn-time recall and write, model tools, agent creation |
| Remote controllers | `packages/api/memory-controller` (existing), new `knowledge-controller`, `agent-center-controller`, `plaza-controller`, `evolution-controller` | Host services exposed to the Client as narrowed Remote namespaces |
| Remote assembly | `packages/api/remotes` | Must select every new namespace and forwarded event |
| Transport | `packages/api/gateway` | Typed unary calls, mux streams, event forwarding; owns nothing domain-specific |
| Presets | `packages/preset/agent-preset-registry` | Declarative agent definitions and revision retention; the evolution result lands here |
| Persistence | `packages/session/*`, `packages/storage/*` | Durable event log and non-session storage |

Each new package follows the repository rules: service packages default-export the service class; function plugins named-export `name`, `inject`, `Config`, `apply`; registrations go through `ctx.effect` / `ctx.on`; optional services are read with `ctx.get(name)`.

## Capability seams

### Memory

The seam keeps its shape: a Service Definition, one provider, and consumers. Two additions:

- **Turn-scoped exclusion.** Recall returns entry identities; the loop's prompt assembly drops excluded identities for that turn and records the exclusion as a durable event so replay reproduces the same prompt.
- **Correction as a version.** `correct` appends a new entry version with provenance to the previous one. Library reads resolve the latest version; timeline reads show all.

### Knowledge

A new seam with the same three roles. The Service Definition owns: collection membership, item versions with effective dates, citation resolution, promotion proposals, the access/purpose grant model, and index versions. Providers own storage, chunking, embedding, and retrieval. Consumers are: prompt assembly (citation injection), the `knowledge` model tool, the knowledge center Remote, and the agent grant resolver.

Rules the Definition enforces, because a UI cannot:

- A promotion is a proposal object with an approver and a destination; no API path moves an item in place.
- Grants name collections and tiers, never item lists.
- Index versions coexist; a query is answered by exactly one active version per collection, and a cutover is atomic.
- Citation resolution returns the version that was cited, not the current one; a stale citation is a first-class value.

### Execution records

A consumer in `packages/memory` and `packages/core/agent-loop` boundary: the loop emits one record per agent-driven turn without owning the record's storage. The record store lives in `packages/storage` with a repository package in `packages/agent-center/records` (new).

Record fields are fixed at write time: agent id, version id, adaptation revision, working directory class, trigger class, outcome with cause class, token and duration measures, tool call counts by tool, approval wait time, signal list, and event provenance references. No transcript content is stored; a record field that would carry private text stores a reference only.

Records are append-only; correction appends a successor record with a `supersedes` reference.

### Evolution report

The generator is a service in `packages/agent-center/evolution` (new). It reads a record window and a memory scope, computes metrics and trends, extracts recurring correction patterns, and asks the model to propose typed changes over the fixed target set. The model never receives raw transcripts; it receives aggregates and cited signals. Every proposal must carry at least one citation or it is dropped before the report is stored.

Approval is a Host operation that: validates the report is in `in review`, records the approver principal, runs shadow evaluation against recorded sessions, and on success writes a new preset revision through `agent-preset-registry`, activates it, and links the version to the report.

## Durable facts and persistence

New session events, all model-visible facts included:

| Event | Payload purpose |
|---|---|
| `memory/exclusion` | Which entry identities a turn excluded from recall |
| `memory/acceptance` | Submission id, state, cause class |
| `knowledge/citation` | Collection, item, version, effective date, tier |
| `agent/execution-record` | Record id and its closed measures snapshot |
| `evolution/report-state` | Report id, state transition, approver, version id |

Each is a `SessionEventMap` member with `@mode` and `@param` JSDoc; a new model-visible input requires its event, per the `model-visible ⟺ logged` rule. Bump `SESSION_FORMAT_VERSION` only when existing discriminators cannot prevent unsafe interpretation; otherwise readers must tolerate an unknown-newer event.

Records also need non-session storage: the record store, report store, and plaza catalog are `storage` consumers with their own schema versions, independent of `SESSION_FORMAT_VERSION`. Deleting a user's records removes measures and keeps an anonymized existence marker for cost and audit totals.

## Permissions, tenancy, and governance

- Every Remote endpoint declares the resources it touches; the knowledge namespace resolves `collection` and `tier` resource kinds through `typert.resources` so a non-owner Peer cannot read what the policy does not admit.
- External sharing requires a policy-owner principal, produces an audit entry, and carries an expiry enforced at read time.
- Enterprise holds mark records as non-deletable for a declared period; the UI receives the hold state as a field, never infers it.
- Takedown of a plaza version stops new installs and leaves forked copies intact; the catalog row is immutable, and takedown appends a state event.

## Provider integration (MemoryBear and beyond)

The shipped MemoryBear provider is unchanged in shape. Two capability questions must be answered before the product surfaces go live, per the integration plan:

- Whether separate end-user bindings isolate workspace scopes across write, recall, list, and profile, or whether the backend needs an explicit scope field.
- Whether deletion and graph endpoints exist behind the management API, which decides whether the delete, graph, and forgetting views can be shown at all.

Until both are answered, the controller returns `degraded` with a cause class, and the UI stays in the states defined by the design's state model.

## Observability

Per-turn structured telemetry: recall latency and hit count, exclusion count, knowledge citation count, record write failure, report generation duration, approval latency, shadow evaluation failure rate, install confirmation rate, and external share creation. Every failure carries a cause class from a closed union, so dashboards distinguish provider unreachable, degraded, and refused.

Alerts worth standing up on day one: index cutover with a rising answer-change rate, records older than the comparison window without a report, unknown-write states above a threshold, and any grant widening that names an audience larger than the collection's tier allows.

## Testing

- Capability-seam tests: a Definition test with a fake provider for memory and knowledge; consumer tests asserting prompt assembly, citation rendering, and exclusion replay.
- Remote tests: descriptor generation, access-control denial through the executor (not through schema omission), and unknown-outcome behavior.
- Persistence tests: new events round-trip, replay reproduces prompts, and a migration read path returns `migration-required` rather than guessing.
- Report pipeline tests: citation required, shadow failure blocks promotion, rollback restores the previous revision.
- Both SDKs' expected outputs update in the same change when loop, session, or event shapes move.

## Delivery order

1. Memory controller extensions (scope, cursor, exclude, correct, timeline) and the acceptance events.
2. Execution record emission and the record store.
3. Evolution report generation, shadow evaluation, and approval writing a preset revision.
4. Knowledge seam Definition, a first provider, and the knowledge controller.
5. Plaza catalog storage, install diff, publish gates.
6. Governance: holds, external sharing audit, takedown state.

## Risks and mitigations

| Risk | Mitigation |
|---|---|
| Record volume grows without bound | Retention per tier, aggregation before storage, and a hard per-agent cap |
| Report generator optimizes for approval instead of outcomes | Shadow evaluation plus the post-application comparison window; a regressed version is flagged for rollback automatically |
| Promotion leaks private text into organizational authority | Proposal object with named approver, redaction field, and no in-place move path |
| Index cutover silently degrades answers | Fixed evaluation query set, side-by-side index versions, atomic cutover, retained rollback |
| Stale citation presented as current | Citations carry the cited version and effective date; resolution never rewrites them |
